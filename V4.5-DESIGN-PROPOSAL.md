# V4.5 Pre-Experiment Pipeline — 详细设计方案

> **驱动 (用户 2026-04-29)**:
> - V2/V3 6 阶段太臃肿 (init→survey→axiom→propose→dispatch→loop)
> - V4 4 阶段砍太多 (decompose→locate→feasibility→plan) — 丢掉了"范式摩擦"价值
> - 需要收敛 + 保留摩擦力 + 并行 ideation
>
> **新结构**: 实验前 = superpowers brainstorming/writing-plans; 实验后 = GSD phase-state-machine

---

## Part 1 — 三个版本对账

### V2/V3 链路 (paper-anchored, sequential, bloated)

```
init → survey → axiom → propose → dispatch → loop → review (7 stages)
       └─ 红海: papers → axioms → reframe 同一假设空间                ─┘
       └─ 串行: 每阶段等前阶段完成,~50min/cycle                       ─┘
       √ 保留: 范式摩擦力 (axiom rewriting), 公理脱轨思路             ─┘
```

**优点**: 摩擦力机制 (在 axiom 阶段抽 hidden assumption + propose 阶段做 reframe)
**缺点**: 阶段太多 + 红海 (从 paper 出发) + 串行 (latency 高)

### V4 链路 (rules-first, isolated, convergent)

```
rule yaml (用户给/Gemini 拆) → decompose → locate → feasibility → plan (4 stages)
                                                                        └─→ run
                                                                        └─→ verify
```

**优点**: 收敛 + 上下文隔离 + 验证为目的 + 模型分工固定
**缺点**: **砍掉了 friction 价值** — friction.yaml 还在 cron 里产, 但 v4 命令链路不直接消费它; rule 怎么来的?如果是 paper-derived 还是红海

### V4.5 提案 (三步法, 保留摩擦力, 并行 ideation)

```
Step 1 拆解 (decompose)        — parallel Opus + Gemini
Step 2 分析 (placement)         — parallel 4 axes (data/arch/loss/train)
Step 3 解答 (novelty + design)  — Scholar filter → plan.md
```

**优点**: 3 步比 V2 收敛 50%, 比 V4 多 1 步但保留 friction; 并行在 ideation 层而非 dispatch 层 (不需要 9 niche)

## Part 2 — V4.5 三步法详细设计

### Step 1 — 拆解 (Decompose) Opus + Gemini 并行双引擎

**目的**: 把 1 个研究问题拆成 (constitution + rules + first_principles + frictions) 4 维结构。

**模型分工**:
- **Gemini 3 Pro**: 第一性原理拆解 (math/physics/CS atomic predicates)
- **Opus 4.7**: 宪法 + 规则 + 摩擦面 (constitution-level rules + hidden assumptions + friction surface)

**为什么并行**: 两个引擎从不同角度切入, 互补 — Gemini 强在演绎链, Opus 强在政策级 (rules) 抽取。

**输入**: 1 个研究问题 (用户输入或 paper-derived 都行)。

**输出** (4 个 yaml,放 `~/research/v4/decompositions/<topic>/`):

```
decompositions/<topic>/
├── first_principles.yaml      ← Gemini: P1, P2, ... atomic predicates + 演绎链
├── constitution.yaml          ← Opus: R1, R2, ... rules paper IMPOSES (sourced from related papers)
├── assumptions.yaml           ← Opus: A1, A2, ... hidden assumptions to challenge
└── frictions.yaml             ← Opus: F1, F2, ... derailment opportunities (cross-link first_principles ⊗ rules ⊗ assumptions)
```

**关键: 摩擦面 (frictions.yaml) 保留 V2/V3 价值**:

每个 friction = (target_layer + attack_vector + new_idea_seed)。这是 V2 axiom-rewriting 的核心,V4 砍掉了,V4.5 找回。

**命令**: `/v45-decompose <topic>` — 单 message 同时调 Gemini + Opus,2 个 parallel agents。

### Step 2 — 分析 (Placement) 并行 4 轴 ideation

**目的**: 对每个 (rule × first_principle) 组合, 并行思考"放在哪个位置能验证它":
- **Data axis**: 哪个 dataset 能暴露 friction?
- **Architecture axis**: 哪个 model arch 能体现 first_principle?
- **Loss axis**: 哪个 loss function 能放大 rule 效应?
- **Training axis**: 哪个 training strategy 能让 friction 浮现?

**为什么并行**: 4 个 axis 互相独立,不需要顺序。1 rule × 4 axis = 4 placement candidates per rule。

**输入**: Step 1 的 4 个 yaml。

**输出** (放 `~/research/v4/placements/<topic>/`):

```
placements/<topic>/
├── data-placements.yaml        ← {rule_id, dataset_candidates, why_fits, scholar_evidence}
├── arch-placements.yaml        ← {rule_id, arch_candidates, why_fits}
├── loss-placements.yaml        ← {rule_id, loss_candidates, why_fits}
├── train-placements.yaml       ← {rule_id, train_strategy_candidates, why_fits}
└── cross-products.yaml         ← top-K (rule × data × arch × loss × train) tuples
```

**模型分工** (4 parallel Sonnet 4.6):
- 每个 axis 由 1 个 sonnet subagent 处理
- 用 superpowers:dispatching-parallel-agents skill 在单 message 启动 4 个 parallel calls
- 每个 axis 内部用 `mcp__scholar__scholar_search_top` 找 dataset/arch/loss/train 的高引用候选

**命令**: `/v45-analyze <topic>` — 4 parallel agents,每 agent 8 min, 总时长 = max(8min) 而非 32min。

**保留 V2 价值**: cross-product yaml = V2 的 propose top-K reframes,但带 placement 4 维信息,更具体。

### Step 3 — 解答 (Novelty + Design) Scholar 过滤 + plan.md

**目的**: 对 cross-products.yaml 的每个 (rule × data × arch × loss × train) tuple, 用 Scholar 查重,保留 novel 的 → 写实验 plan.md。

**模型分工**:
- **Codex GPT-5.4**: novelty audit (Scholar 查重 + 训练-cutoff 内查重)
- **Opus 4.7**: 实验 plan.md 写作 (基于 superpowers:writing-plans 格式)

**输出** (放 `~/research/v4/experiments/<topic>/`):

```
experiments/<topic>/
├── novelty-filter.yaml         ← Codex 输出: tuple_id, scholar_evidence, status (novel/near-match/published)
├── surviving-tuples.yaml       ← 通过 novelty filter 的 tuple 列表
├── plan.md                     ← Opus 写: 完整实验计划 (superpowers-style)
├── plan-shortlist.md           ← top-3 implementation candidates
└── decision-trace.jsonl        ← 每步决策的 audit 记录
```

**plan.md 格式** (superpowers:writing-plans 兼容):

```markdown
# Experiment Plan — <topic>

## Hypothesis
If <rule R-X applied at <placement>>, then <metric> shows <effect>, because <first_principle P-Y>.

## Implementation steps (TDD per superpowers:test-driven-development)
1. [ ] Write tests/test_<rule>.py — measures <falsifier metric>
2. [ ] Implement minimal model with <arch placement>
3. [ ] Apply <loss placement> + <train placement>
4. [ ] Run on <data placement> — write results.tsv
5. [ ] Verify rule per falsifier criterion

## Verification (superpowers:verification-before-completion)
- Test passes: <criterion>
- Metric threshold: <number>
- 5-min kill: <experiment that falsifies>

## Hand off (post-experiment)
→ /gsd:gsd-execute-phase  (post-experiment Pipeline = GSD)
```

**命令**: `/v45-design <topic>` — Codex novelty + Opus plan, 顺序执行 (novelty 必须在 plan 之前)。

## Part 4 — V4 → V4.5 迁移路径

| V4 现有 | V4.5 改动 |
|---|---|
| `/v4-rule-decompose` (单引擎 Gemini) | 升级为 `/v45-decompose` (Opus + Gemini 并行,4 yamls 输出) |
| `/v4-rule-locate` | 升级为 `/v45-analyze` (4 axes 并行 placement,不只 dataset) |
| `/v4-rule-feasibility` | 拆为 `/v45-design` 第 1 步 (Codex novelty filter) |
| `/v4-experiment-plan` | 升级为 `/v45-design` 第 2 步 (Opus 写 superpowers plan) |
| `~/research/v4/rules/R-XXX.yaml` | 保留, 但作为 `topic` 的子产物 (rule 是 decompose 输出之一) |

**关键: V4 的 rule yaml 不丢, 但层级降一级**:
- V4: rule = 顶层输入 (用户直接给)
- V4.5: rule = decompose 的输出 (用户给 topic, 系统 decompose 出 rules + first_principles)

## Part 5 — 与 superpowers / GSD 的接口

**实验前 (V4.5 自己处理)**:
- `/v45-decompose` 内部用 `superpowers:brainstorming` skill (Opus 端)
- `/v45-analyze` 内部用 `superpowers:dispatching-parallel-agents` skill (4 axes 并行)
- `/v45-design` 输出的 plan.md 兼容 `superpowers:writing-plans` 格式

**handoff 到 superpowers (实验前最后一步)**:
- `superpowers:executing-plans` 读 plan.md → spawn TDD session 执行实验

**handoff 到 GSD (实验后)**:
- 实验结果 → `/gsd:gsd-discuss-phase` (clarify findings)
- → `/gsd:gsd-plan-phase` (paper-writing PLAN.md)
- → `/gsd:gsd-execute-phase` (写 paper draft)
- → `/gsd:gsd-verify-work` (UAT = paper internal review)
- → `/gsd:gsd-ship` (submit to ICLR/ICML/NeurIPS)

## Part 7 — 三个 V4.5 命令骨架

### `/v45-decompose <topic>` — 双引擎并行

```bash
# Single message, 2 parallel calls
parallel:
  - Agent(subagent_type="general-purpose", model="claude-opus-4-7",
          prompt="Use paradigm-friction-extractor skill on the topic <topic>.
                  Output constitution.yaml + assumptions.yaml + frictions.yaml.")
  - gemini --approval-mode=plan -m gemini-3-pro-preview
           "<first-principles decompose prompt>"

输出: 4 yamls in decompositions/<topic>/
```

### `/v45-analyze <topic>` — 4 axes 并行

```bash
# Single message, 4 parallel Sonnet calls
parallel:
  - Agent(model="sonnet", prompt="Data placement: 给定 frictions.yaml,
          每条 friction 找 3 candidate datasets, 调 mcp__scholar__scholar_search_top")
  - Agent(model="sonnet", prompt="Architecture placement: ...")
  - Agent(model="sonnet", prompt="Loss placement: ...")
  - Agent(model="sonnet", prompt="Training placement: ...")

输出: 4 placement yamls + cross-products.yaml (top-K tuples)
```

### `/v45-design <topic>` — Codex + Opus 顺序

```bash
# Sequential
1. codex exec --model gpt-5.4 "novelty audit on cross-products.yaml,
                                Scholar query each tuple, mark novel/near-match/published"
2. Agent(model="opus", prompt="Write superpowers-ready plan.md
                                from surviving-tuples.yaml")

输出: novelty-filter.yaml + plan.md (ready for superpowers:executing-plans)
```

## Part 8 — 决策点 (启动前等用户回答)

1. **decomposition 引擎组合**: Opus + Gemini 并行 (推荐) vs 单 Opus (快但同质)?
2. **placement 4 axes 是否够**: data/arch/loss/train (推荐) vs 加 hyperparam/prompt 6 axes?
3. **novelty filter 严格度**:
   - 严格 (任何 near-match 都 drop) — 安全但产出少
   - 松 (full collision 才 drop) — 产出多但有重复风险
4. **decompositions 是否复用**: 同 topic 跑过 decompose 后, 后续直接用现成 yaml vs 每次重新拆?
5. **rgmare-lite 处理**: 完全 deprecate vs 保留 friction.yaml cron 作为 v4.5 的 paper-corpus 输入?

---

## Part 9 — 一行总结

> **V4.5 = V2 摩擦力价值 + V4 收敛性 + 并行 ideation 在 placement 层**
> **3 步法**: 拆解 (Opus+Gemini 并行) → 分析 (4 axes 并行) → 解答 (Codex novelty + Opus plan)
> **实验前用 superpowers, 实验后用 GSD** — 各取所长, 不混用
